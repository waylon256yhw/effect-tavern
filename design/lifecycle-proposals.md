# 回合生命周期拓展与工序解耦提案

2026-10-25。区别于 `docs/` 下对现有生态材料的事实拆解，本目录存放面向下一阶段的架构提案（Proposals）。

本篇记录围绕「如何用确定性的分阶段生命周期替代传统酒馆预设的大浆糊」展开的四个设计方向：三段式工序的声明式拓展、基于 `Part` 的一次性场外附言块、事后检验层（`check`）的综合反八股化，以及 Provider 层的按工序路由。

---

## 1. 背景：从「提示词魔咒预设」到「生命周期乐高」

传统酒馆预设在运行时只有唯一一把锤子：**单次请求、单个模型、一段混装文本**。无论是前置的导演构思、正文撰写、幕后小剧场，还是事后的状态总结与选项生成，都被迫塞进同一次生成里，靠提示词魔咒和成堆的正则按楼层深度硬切。其代价是语义边界模糊、上下文互相污染、缓存频繁失效，且所有子任务被迫绑死在同一个模型上。

本项目的回合骨架已经在代码层面将一轮交互拆成了职责明确的有类型工序：

```
lookup → (decide → settle)* → gate → direct → narrate → check → record
```

在这个骨架之上，高阶预设（Enhancer）与卡创作者的能力不应止步于「往头区塞几句文风提示词」，而应沿着**前置引导（Director）→ 实际撰写（Writer / Narrate）→ 事后验收与归档（Checker & Record）**三个核心切面，以声明式的数据结构（可求值、可画 GUI、可解码的「三张脸」）按需拼装。

## 2. 一次性场外附言块（Ephemeral Stream Blocks）

### 2.1 痛点与本质

在生态实践（如「小猫之神 / Reborn」等预设，见 `docs/preset-reading-2.md`）中，有两类极受玩家与创作者欢迎、但此前在本项目中尚无归宿的玩法：

1. **文内前置构思（In-text CoT / 演绎导读）**：针对没有原生 `thinking` 能力或容易落入刻板套路的中小模型，要求其在写正文前先按固定格式写一段构思（出场人物、运镜焦点、潜在创新表现），作为自回归生成的垫脚石。
2. **幕后彩蛋与场外互动（小剧场 / 角色吐槽 / 作者留言 / 下集预告）**：在正文结束后附带一段轻松的场外内容，只供玩家当轮阅读找乐，不属于故事正史。

这两件事在底层具有完全相同的生命周期本质：**它们都是在 `narrate` 阶段顺带生成的、只给玩家看一眼的一次性内容，绝不能进入下一轮的历史上下文，也不能被当成正史事实。**

### 2.2 为什么不能全塞进 `record` 阶段的 `Product`？

`record` 是冷提取器（`temperature: 0, effort: "off"`），且其请求只包含 `frame`、`Known` 与当轮正文，**不包含 `card.fiction`（角色详细设定）和 `history`（对话转录稿）**。

- 像 `notes`（事实摘要）、`people`（人物表）这类客观提取归 `record`；
- 但像「文内构思垫脚石」（必须在正文第一个字之前同流生成才能发挥自回归近因效应）和「幕后小剧场 / 角色口吻留言」（依赖完整角色人设、历史对话语境与高创造力采样），**只有挂在已经命中 KV Cache 的 `narrate` 阶段顺手生成，才能做到零额外输入 Token 成本且角色语气满血**。

### 2.3 机制设计：复用 `journal.ts` 的 `Part[]` 接缝

无需在正文上跑事后正则清洗，直接沿着现有的 `Turn.reply: readonly Part[]` 接缝扩展：

1. **声明**：玩家层或卡声明需要在 `narrate` 中附带的场外块（`id`、展示 `label`、位置 `before | after`、生成要求 `text`）。
2. **流式切分**：`narrate` 流式接收器识别约定定界符，将块内容直接切分为非 `text` 类型的 `Part`（例如 `{ type: "aside", id, label, text }`），正文部分照常作为 `{ type: "text", text }` 流出。
3. **天然的四重隔离**：
   因为全系统读取正文均通过 `prose(t)`（即 `parts.filter(p => p.type === "text")`），任何非 `"text"` 的 `Part` 自动获得以下性质，无需在各阶段写特殊分支：
   - **不污染后续历史（`narratorHistory`）**：下一轮拼接历史时只取 `prose(t)`，模型在后续轮次完全看不到上一轮的小剧场或文内构思，杜绝画风跑偏与格式滚雪球。
   - **不干扰事后护栏（`check`）**：`check` 只检查 `prose(reply)`，小剧场里的戏言不会误触发 `guard` 规则或冒领 `must` 揭示。
   - **不污染正史提取（`record`）**：`record` 只读 `prose(reply)`，场外玩笑不会被记入 `notes` 摘要，也不会影响 `readouts` 状态判定。
   - **前端原生可画**：该块完好保存在节点的 `turn.reply` 中，UI 可按 `id / label` 将其渲染为折叠面板、小剧场卡片或页边批注。

## 3. 三段式工序的声明式拓展（Director & Checker）

目前 `record` 已通过 `Product` 实现了「创作者声明 Schema」，后续可将同一模式延伸至前置导演与事后检验：

### 3.1 Director（前置导演任务项）

- **现状**：`direct` 阶段目前仅在有 `offer` 窗口开启时运行，且输出固定为 `Brief = { must, may, tone }`。
- **拓展**：允许创作者或高阶预设声明自定义的导演规划字段（如本幕冲突推进点、叙事节奏、视角焦点），在 `direct` 阶段以结构化 Schema 产出，并由代码格式化后注入 `narrate` 尾区的简报中。把传统预设里混在正文前的「思考步骤表」变成真正受代码管束的独立工序。

### 3.2 Checker（综合的事后检验与反八股 / Anti-slop）

- **现状**：`check` 阶段目前仅校验 `must` 揭示是否命中、`guard` 剧情禁令是否违反，表达力较单一。
- **痛点**：为防止模型写出高频套话（如「手指收紧又松开」「指节发白」「一丝不易察觉」「不是……而是……」），目前只能将禁令塞进 `style` 槽位。这既占用每轮头区 Token，又容易引发「粉红大象效应」（禁令本身把套话激活在模型注意力中）。
- **拓展**：将文风质检、禁用词表与去 AI 味（Humanizer / Slop 过滤）沉淀到 **`check` 阶段**，分两层执行：
  1. **代码级确定性校验（0ms，不调模型）**：
     - **八股/禁用表达词表（Slop Lexicon）**：扫描当轮 `prose` 是否命中创作者或玩家挂载的禁用词组、句式模板或近义替换表。
     - **跨轮意象复读检测**：比对最近 $N$ 轮正文，拦截高频重复的景物或微动作收尾（如连续三轮以「雨珠滴落青石阶」收束）。
  2. **模型级综合验收与定向重写**：
     - 平时 `narrate` 的提示词保持干净，不背负长串负面禁令；
     - 仅当某轮草稿实际撞上代码词表或 Checker 规则时，才将**当轮命中的具体病灶**拼入 `narrate.correction` 触发重写（或交由轻量润色器做局部近义替换），从源头保证落库并进入下一轮历史的文本干净无口癖。

## 4. Provider 层的工序级路由（Stage-to-Connection Binding）

`src/session.ts` 在设计之初便预留了接缝注释：`a real harness binds stages to connections`。

### 4.1 为什么分阶段架构天然适合多模型混搭？

在 `src/request.ts` 中，六个阶段的上下文视图本来就是分离的：
- **唯一的长上下文创作调用是 `narrate`**：只有它读取完整的 `card.fiction` 与 `history` 转录稿，也只有它依赖长前缀的 Prompt Cache。
- **其余五个阶段（`lookup`、`decide`、`direct`、`check`、`record`）全是短上下文的结构化判别与提取**：它们只读 `frame` 加事实账本或单轮正文，运行在 `temperature: 0, effort: "off"` 下。

这意味着：**将结构化阶段路由到其他模型或 Provider，完全不会打断 `narrate` 主力模型的 Prompt Cache。**

### 4.2 路由模型形状

将 Session 所接收的单一 `SessionModel` 扩展为带默认回退的工序路由表：

```ts
export interface StageModels {
  default: SessionModel
  stages?: Partial<Record<Phase, SessionModel>>
}
```

典型配置组合：
- **`narrate`（Writer）**：绑定文笔上限最高的主力创作模型（如 Claude Opus / Sonnet、Gemini Pro 或专项写作微调模型），开启 `1h` 缓存 TTL。
- **`lookup` / `decide` / `check`**：绑定极速、低成本且原生 JSON Schema 稳定的轻量模型（如 Haiku、Gemini Flash-Lite），将前置判别与事后验收的延迟压到百毫秒级。
- **`direct` / `record`**：按需绑定高性价比的中等模型（如 Flash / Haiku），专门负责导演调度与多字段表格提取。
