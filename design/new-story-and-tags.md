# 新建故事页、双层标签与混合搜索设计（讨论纪要与提案）

2026-11-01。本篇记录在进入下一阶段功能开发前，关于**词汇定调（Glossary 内隐与外显）**、**游玩与制卡的信息边界（`CardPage` vs `Workshop`）**、**新建故事页改版方向**、**人设粒度**以及**标签系统与混合搜索**的整体思考。

---

## 1. 术语与定词原则：取实不取形，内隐与外显分层

在设计卡片信息抽取与界面呈现前，首先明确术语表（[`GLOSSARY.md`](../GLOSSARY.md)）的作用边界：

1. **借的是「实」（概念边界与分类法），不是「形」（表面包装）**：
   - 引入戏剧、电影与叙事学术语（如 `diegetic / non-diegetic`、`homodiegetic / heterodiegetic`、`dramatic irony`），是为了解决旧生态中概念混杂的问题（例如将心声与 OOC 混为一谈、将常驻设定与渐进披露混在“世界书”里）。
   - 一旦底层结构按正交边界切分清楚，落到字面上的名字只要日常词或 AI RP 社区共识词本身是准确的，就必须保持平实，绝不为了表面风格把「开场白」改叫「序幕」、把「提示词」改叫「底本」。
2. **三层受众的内隐与外显**：
   - **Dev 与协作者 AI（架构与代码层）**：追求概念正交、无歧义（内隐）。
   - **LLM（`request.ts` 的 `asks` 指令层）**：使用能直接激活模型文学与叙事学先验的行业通用词（内隐）。
   - **玩家与卡作者（UI 界面层）**：使用零理解成本、符合社区直觉的平实词汇——**开场白、提示词、`tokens`、人设、参与者 / 作者、状态、检定、读数、线索、标签**（外显）。

## 2. 游玩与制作的信息边界：`CardPage`（新建故事） vs `Workshop`（制卡工坊）

目前左栏单卡工作区（[`side.tsx`](../packages/client/src/side.tsx)）已将入口彻底分离：点击顶部卡头进入 `Workshop`，点击底部「＋ 新建故事」进入 `CardPage`。两者的职责与信息分配随之解耦：

| 维度         | 新建故事（`CardPage` · 游玩侧）                                                                                                                                                      | 制卡工坊（`Workshop` · 制作侧）                                                                                                                                                                                              |
| :----------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **定位**     | 玩家进入故事前的开局页（选定开场白、建立规模与玩法预期、开始新局）                                                                                                                   | 面向 `Card` Schema 的结构化制作与解剖台                                                                                                                                                                                      |
| **展示内容** | **100% 可由程序自动提取、分块的内容 + 用户标签**：<br>标题、标签（`tags`）、简介（`summary`）、客观规格（视角模式、提示词与开场白 Token 计数、规则机制计数）、开场白正文及多开场切换 | 完整 `Card` 数据：Frame 槽位、Fiction 模块与 `when` 状态分段、Greetings 与 `do` 初始效果、Rules（字段/动作/读数/终局）、Lore 分层门控、Guard、Products、Lexicon 及 [`lint.ts`](../packages/runtime/src/lint.ts) 实时拓扑诊断 |
| **明确剔除** | 不再把内部 `fiction.label`（如《伴星》的 `依瑞丝 · 示范`）当“设定”透传给玩家；不放需要人工造句的非标玩法长文案；不放解释性小字旁白                                                   | 不作为新建故事的第二入口                                                                                                                                                                                                     |

## 3. 新建故事页（`CardPage`）的现存痛点与重构方向

针对当前 [`card.tsx`](../packages/client/src/card.tsx) / [`card.css`](../packages/client/src/card.css) 原型的三个具体问题：

### 3.1 尺寸与空间：去掉“卡中卡”拘束，撑满主舞台

- **痛点**：`.stage-card` 本身已是主舞台大卡片，但 `.cardsheet` 又在内部居中画了一个 `max-width: 56rem; height: 24.5rem` 的弹窗式盒子，导致外围留白浪费、内部 600～800 字的长开场白只能在 `16.5rem` 高的小框里局促滚动。
- **方向**：取消居中小盒子的高度与阴影限制，直接以 `.stage-card` 为画布舒展排布；右侧（或下部）开场白阅读区的字号、行宽（measure）与纵向空间向阅读器（`Reader`）对齐，让第 0 轮开场白的阅读体验与正文无缝衔接。

### 3.2 信息与分区：去线条化，以自动提取的分块内容重排

- **痛点**：中间通顶竖线（`border-right`）与左侧底部横线（`border-top`）切割生硬；当简介较短时，左侧中段出现大面积无意义的空白，而左下角透传的 `设定: 依瑞丝` 对玩家了解玩法毫无帮助。
- **方向**：
  1. **拿掉生硬的横竖分割线**，改用版面留白、字阶层级与温和的底色差（Surface Contrast）区分导览信息与开场白正文。
  2. **清理无意义透传，只留高价值量化与结构信息**：
     - **保留并突显 Token 计数**：`提示词 ~1.2K tokens`（常驻设定体量与上下文成本预期）与 `开场白 ~691 tokens`（作为续写范例的篇幅与耗时预期）是熟练玩家判断卡片规模的核心锚点，必须透明呈现。
     - **用「双层标签 + 结构计数」替代原来的 `设定` 行**（见第 5 节）。
     - **多开场白（Greetings）的结构化分块**：利用现有的 `firstLine(g.text)`（首句提取）、`openingTag(c, g)`（初始状态赋值如 `起点 = 血案`）与单篇 Token 计数，让多开场分支能够直观预览和切换，而不是藏在右下角极小的数字弹出菜单里。

## 4. 关于人设（Persona）的粒度与位置

1. **为什么不在「新建故事页」放人设选择器**：
   - 在当前桌面与移动端壳层中，左侧单卡工作区（`.workspace-tools`）已常驻展示了「人设」与「写作」两行入口，在右侧舞台内重复放置会造成同屏冗余。
   - 同时移除 [`card.tsx`](../packages/client/src/card.tsx) 中历史遗留的 `<Show when={persona()}>` 行与多余的说明小字。
2. **数据粒度演进思考（卡级 vs 局级）**：
   - 目前代码中人设仅按卡存储（`Player.persona[card]`）。但从实际游玩的自由度与细腻度来看：
     - **强剧情依赖卡**通常使用卡片默认人设，或整张卡固定一个微调人设（偏卡级）；
     - **散文卡、大世界卡、多路线开场卡或模板化 RPG** 中，玩家常在同一张卡下开多局（甚至多 Tab 并行），不同局扮演完全不同的身份（偏局级）。若仅有卡级存储，在一局中切换人设会静默串改同一张卡下的其他局。
   - **后续方向**：往**「卡级记住默认选用，局级（`story`）可独立持有/覆盖」**演进——新建故事时继承该卡当前选用的人设，在某一局内切换人设只影响当前局（或明确区分卡默认与本局人设），避免多局串台。

## 5. 双层标签系统与混合搜索（Hybrid Search）

为了让标签既能服务「新建故事页」的快速认知，又能支撑左栏卡架（Shelf）的全局筛选，采用**「Harness 自动抽取规格 + 用户层自由标签」**的双层模型：

### 5.1 标签的归属分层

1. **第一层：系统客观特征（归 Harness，100% 从 `CardView` 自动抽取）**
   无需作者手写，代码按卡片结构确定性算出，全系统词表封闭且天然支持中英 i18n：
   - **视角模式**：`参与者`（`input: "act"`） / `作者`（`input: "note"`）
   - **机制特征（有则生成，无则不显示）**：
     - `状态`（含可见 `rules.fields`）
     - `检定`（含 `rules.actions`）
     - `读数`（含 `rules.readouts`）
     - `线索`（`lore.entries > 0`）
     - `多开场`（`greetings.length > 1`）
   - **Token 规模**：`提示词 ~1.2K tokens` / `开场白 ~691 tokens`。
2. **第二层：内容与风味标签（归用户层：卡作者与玩家，`Card.tags?: string[]`）**
   - 在 `Card` Schema（及 `GET /cards`、`GET /card` 投影）中新增可选的 `tags: string[]`。
   - 卡作者在制卡时自由定义题材、风格、关系等标签（如 `["日常", "纯聊天"]`、`["武侠", "对峙"]`）；玩家在本地 `Workshop` 中也可随时增删改，用于本地归档与筛选。Harness 不内置题材枚举，也不对用户标签做翻译。

### 5.2 融合进现有搜索框的「混合搜索器」

在不增加左栏卡架常驻高度的前提下，将标签过滤无缝融进现有的单行搜索框（[`side.tsx`](../packages/client/src/side.tsx)）：

1. **统一查询词法（#标签 + 系统特征 + 纯文本 AND 交集）**：
   - 搜索框输入按空格切分词元：
     - **普通文本词**：同时匹配 `title`、`summary` 与 `tags`；
     - **`#标签` 词元**：精确匹配用户标签（如 `#武侠`）或系统自动特征（如 `#作者`、`#检定`、`#多开场`）；
     - **排除前缀 `-`**：如 `-#检定` 或 `-#纯聊天`，快速排除特定类型。
2. **视觉点选与文本输入双向联动**：
   - **聚焦候选面板**：平时保持单行搜索框；当搜索框聚焦或输入 `#` 时，下方浮出当前卡架上实际存在的「系统特征胶囊」与「高频用户标签胶囊（含命中计数）」，点击即填入/切换过滤条件，剩余计数随筛选实时收敛（Faceted Search）。
   - **页面标签可点**：在「新建故事页」上点击任意标签，可直接联动卡架筛选出同类卡片。
