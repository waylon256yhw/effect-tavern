# 读卡记录：五张典型角色卡的两个方向

2026-10-09。读了五张生态里的角色卡，每张从两个方向看：代码方向（harness 拿它做什么）和语文方向（作者在写什么、对谁说）。目的是让后续设计讨论有实感，不是做兼容。五张卡由讨论者挑选为典型形态，不是普查样本。

## 1. 格式基线：Character Card V2 / V3

V2 规范：https://github.com/malfoyslastname/character-card-spec-v2（2023 年 5 月通过）。V3：https://github.com/kwaroran/character-card-spec-v3。对提示词装配有影响的 V2 到 V3 差异很小：`nickname`、世界书的 `use_regex`、`@@` 装饰器。

| 字段 | 代码侧 | 语文侧 | 本项目的家 |
|---|---|---|---|
| `description` `personality` `scenario` | 拼进头区的三段文本 | 自由写法，知识与命令常混在一段里 | 角色层 fragment；知识与命令没有拆开的位置 |
| `first_mes` `alternate_greetings` | 第 0 轮 assistant 消息及其 swipe | 唯一一处作者用叙事者的声音写；示范而非指令 | 节点树第 0 轮兄弟节点 |
| `mes_example` | `<START>` 分隔；ST 解析成 `example_user` / `example_assistant` 的 system 消息，放在历史前，预算不够时第一个被丢 | 声音示范，最定义声音的文本 | 无 |
| `system_prompt` | 默认覆盖玩家全局设置，`{{original}}` 表示保留 | 作者的框架指令 | `fragment.ts` 槽位模式；差别是本项目把开关交给玩家 |
| `post_history_instructions` | 历史之后，替换 jailbreak 槽 | 作者的 must / must-not | 立场：事后 check，不进叙事者提示词 |
| `creator_notes` | 规范禁止进提示词 | 作者对玩家说话 | 无 |
| `character_book` | 关键词扫描；`constant` 常驻；`selective` 是粗糙的 AND；V3 加正则与装饰器 | `keys` 是作者猜玩家会打什么字；`constant` 条目是伪装的框架内容 | 分层条目加 `unlock` / `offer` |
| `extensions` | 不进提示词，不得丢弃 | 不是语文；变量框架把 schema 塞在这里 | 读卡先看这里 |
| 其余 | 元数据 | 无 | 跳过 |

V2 按"落在提示词哪里"分字段，不按"这是哪种写作"分。状态那半边没有规范的家，生态卡把它塞进语文字段；反过来 V3 的 `{{random}}`、`{{roll}}` 和装饰器把代码放进了文本。

ST 对 `mes_example` 的处理（本机源码 `public/scripts/openai.js`、`public/script.js`）：强制补 `<START>`，逐行按"名字加英文冒号"切说话人，第一行无条件丢弃；每段先插 `[Example Chat]`，每句是 role 为 system、name 为 `example_user` / `example_assistant` 的消息；默认先给历史分预算，剩下的才轮到示范，`pin_examples` 才反过来。

## 2. 五张卡

### 2.1 伴星（纯聊天，结构化描述）

V1 + V2 双份，ST 导出。有内容的只有 `description`、`first_mes`、`mes_example`、`creator_notes`，共 2320 tokens。无数值、动作、窗口、规则。

- `description` 是作者自创的结构：Note / Name / Settings / Appearance / Clothing / Emotions。Note 一行是框架（"静谧的文本风格"），写在角色字段第一行。Settings 里有一条语文的 if：对性骚扰平静应对，对温柔关怀极其害羞。它不是状态，不累积，每次由输入触发。缩进表达转折（"懒惰 / 但思想灵活"），压扁成标签就丢。Emotions 写的是动机，给模型即兴用。
- `first_mes` 用玩家的第一人称写，一次定下视角、场景、许可（虚构内部的邀请，无禁令）、主题。明说"今夜还长着呢"：一成不变就是玩法。
- `mes_example` 一组对话，演示 Settings 里那条 if 的触发与收场。规则与示范是一对。
- `creator_notes` 对玩家说话，末尾括号里是 token 数与模型建议。
- `{{char}}` 用了一次，替换结果是作品名"伴星"而不是角色名"依瑞丝"，是错的。

对项目：给这张卡加好感计数器是伤害；record 每轮提 notes、压缩按块折叠，对一张以静滞为目标的卡会累积什么，未解。示范类文本没有槽。

### 2.2 第二张（纯散文，无卡的形状）

约 700 字文本，宏只有旧式 `<user>`，角色名写死，没有 `first_mes`。放进 `description` 后是一条 system 消息。

每条信息都被叙事化：世界只给它造成的后果；角色通过决定立住；玩家被写死（不受欢迎、失业、抑郁、割腕）；关系是一份契约，而且是全文唯一重复的句子，首尾各一次，第二次在割腕之后意思已变；有时间线，现在时在后半段；基调藏在括号旁白里；只有一句元语言（"永远记住最重要的一点"）标记唯一的 must；戏剧反讽开局就全部交给叙事者，不门控。

对项目：编译这段文本的正确输出是一个 fragment，别的什么都没有。玩家槽位冲突是真实的，默认"玩家覆盖卡"会毁掉它。那条契约同时是规则和主题句，抽成 check 规则就失去句子的力量，只当叙事可能被忘。

### 2.3 ·灰色と青（世界书当文档装订器）

V3。`description` 318 字，其余字段空。九条世界书全部 `constant`、无键，四条 `before_char`、五条 `after_char`，按 `insertion_order` 排成十段文件：日记（2006–2015）→ 全家福图注 → 随笔加读书摘录 → 歌词 → 描述（现在时，姐姐）→ 藏了歌名的歌 → 第二人称情欲小品 → 2001 年机关通报（她是超生的第二胎）→ 姐姐的话 → 札记。没有 `{{user}}` 也没有 `{{char}}`，两个人物，不指定扮演关系，无开场白。

角色从未被描述，只被重建。顺序不是时间线，是揭示的节奏，公文按时间该排第一却排第八。标题（赝品、审判、爱的容器）是作者的评语，写进了 content 的标签里所以模型看得见。规则以读书摘录的形式给出。错字模拟年龄。藏起歌名。

对项目：ST 世界书混淆了"带位置的常驻文本"和"受条件露出的知识"，这张卡只用前者，`lore.ts` 一样都不需要。`head()` 把带 `when` 的 fragment 后移以最大化前缀，这张卡全无条件所以无冲突，但冲突的形状已可见。没有 `{{char}}` 的卡要能存在，第一轮输入就是角色分配。作者的功力不可编译。

### 2.4 西西弗斯的恐怖神话（在 ST 内手搭的 harness）

V3。卡本身近空：`first_mes` 是 "poa"。一条正则把每条输出替换成加载远程页面（`ariespo.github.io/maingame/11`，3.6MB webpack 开发包，24 个 TS 模块）的 `<body>`；三个 tavern_helper 脚本（隐藏楼层、MVU、Zod schema）；九条世界书全部 `constant`、无键、`atDepth` 0–4，插在历史尾部。[InitVar] 禁用，前端直接写第 0 楼变量。

前端做的事：自己创建 user 消息并挂变量；按楼层翻转"开局COT" / "COT"；调 `generate` 并流式剥 `<thinking>`；校验 `<maintext>`，失败删 user 消息报错，无自动重问；取最后一次出现的六个标签重拼消息；MVU 解析 JSON Patch 写回本楼；`<sum>` 写进世界书"编年史"条目，编号 `楼层/2 + 1`，每次请求前删掉编号 ≥ 当前楼层的条目以适应重 roll 与读档。

事实：无骰子无种子，一切数值由模型判断，边界用散文请求；`进度等级` 是派生字段也要模型维持一致；隐藏楼层只删 DOM，按代码历史全量送出，含过去的结构化块；`当前世界真相谜底` 前端初始化但 schema 与规则里没有；开场白是远程 JS 的模板字符串插表单值，卡离开 URL 什么都不是。

语文侧很薄，全是 JSON 值形式的元语言。功力在前提（死亡即变异、故乡同位体、重要之人唯一锚、四个真相、下一个宇宙）、嵌在指令里的例句、开局三个同义选项（西西弗斯的玩笑编进机制）。

对项目：这是本项目的论点在 ST 里手搭出来的；状态是嵌套对象、动态记录、模型书写的文本字段；模型每轮生成可选项，玩家从中选，与作者定义动作相反；一万字模板每轮插尾部是作者对近因的选择。

### 2.5 青空 理（MVU 示例卡，读数性状态的对标形态）

来源：https://github.com/MagicalAstrogy/MagVarUpdate/tree/master/example。`Yuki.yaml` 是 tavern_sync 格式的世界书清单，指向十个源文件，是当前版本；`artifact/` 里的基础 PNG 是旧构建（条目名是 `relation_level`、`kokuhaku`），四张变体 PNG 与 yaml 一致。按 yaml 读。没有运行。MVU 框架本身的内部已在 `state-harness-research.md` §2 分析过，这里只看卡。

这是样本里第一张真正的读数性卡：自由聊天加好感度、情绪、时间。十条世界书全部 `constant`、无键，按位置和深度排布：

| 条目 | 位置 | 内容 | 本项目的对应 |
|---|---|---|---|
| 角色信息、NPC信息 | 角色定义前后 | YAML 形式的人设与 NPC | fragment，现有 |
| 变量分阶段-好感度 | 角色定义后 | 28k 字 EJS，按好感度六个区间 `<% if %>` 切换人设文本 | 六个各带 `when` 的 fragment，`cond.ts` 现有，零新代码。README 第三节"模板里的控制流 → 各自带 when 的 fragment"在生态里的实例，五张卡里 `when` 的第一次真实使用 |
| 角色事件-告白 | 深度 0，**role 为 user** | EJS 条件（好感度 ≥ 60 且关系不是恋人或哥哥）成立时注入 `<story_override>`：理会告白；成功与失败各附一组 `_.set` | `aside` 加 `when`。结果由叙事者的正文决定，没有骰子。失败分支最后一行把关系设成"恋人"，从源码看是复制错误；greeting 2 里也带一行无意义的 `_.set(... "m喵");//abc` |
| [InitVar] 初始变量 1、2 | 禁用，由框架读取 | JSON，每个值是 `[值, 说明]` 对 | 说明就是 schema，用自然语言写："[-30,100]之间……变化范围为 [-5,8]"。边界和步进用散文请求，本项目用代码。"数组只更新第一个元素"这条规则存在是因为 schema 和数据存在一起 |
| 变量输出 | 深度 1，system | 每轮把带说明的完整 `stat_data` 送给模型 | 叙事者看见全部数字。本项目立场是叙事者看正文、结构化阶段看事实；"谁看数字"是读数性状态讨论要回答的问题 |
| 变量更新规则、两条格式强调 | 深度 0，system | `<Analysis>` 用英文；`_.set(path, old, new);//reason`；"calculate time passed; decide whether dramatic updates are allowed" | 研究记录 §2.1 批评过的那句话，在卡里看到了：一个判断被写成算术指令 |

卡的扩展字段里：

- **日替脚本**：作者写的唯一一段代码，是一条模型总做错的确定性规则（时间回绕时日期加一）。"代码做算术"的证据，也是具体天花板：时间是字符串状态，`card.ts` 把时间列为天花板。
- **六条正则**：从提示词里剥掉 `<UpdateVariable>`（journal 已分离）；十楼以上把整条消息替换成它的 `<summary>`（生态用正则收敛到了 `history.ts` 的折叠形状）；`<StatusPlaceHolderImpl/>` 替换成给玩家看的 HTML 状态栏、对模型隐藏（从状态渲染的前端）。
- **三条开场白**，各以 `_.set` 结尾设定身份和好感度（15 / 未设 / 60）：第 0 轮是带初始状态的剧本选择器。journal 已允许第 0 轮兄弟节点带拍。
- `first_mes` 是给玩家的 README。作者对玩家这个缺口第二次出现（伴星用的是 `creator_notes`）。

语文侧。作者显然是程序员（webpack、EJS、tavern_sync），仍写了约四万字散文。代码是脚手架，语文是卡。

- **好感度不是分数，是一条写好的弧线的索引**：礼貌 → 变暖 → 朋友带嫉妒 → 占有并自伤（60–80）→ 公开占有（80–90）→ 圆满（≥90）。数字的意义由每一段的文本定义。所谓读数，实际在选择叙事者读到哪段散文。
- 每段是四种情境 × （四条行为 + 四条对白）。行为条是指令，对白条是示范。示范再次出现，这次在条件文本里。
- 角色信息是 YAML 当散文：英文键、中文整句值。`romance` 块与分阶段模板职责重叠。PAD 情绪模型加 `affinity` 是把心理学当状态引入。`<Analysis>` 用英文是作者在告诉模型用哪种语言推理。

对项目：方向 1 有三部分，这张卡确认了全部三个需求，运行时有其中一个。更新发生在写之后、回复尾部（研究记录 §2.1 另记有单独模型模式），确认 record 是位置，运行时未做；有界步进 `[-5,8]` 用散文请求，确认需求，`card.ts` 有边界无步进；阈值切文本，`when` fragment 今天就能做。告白事件的结果由模型决定，本项目的 decide 加 judge 加种子正是作者缺的旋钮。谁看数字，未答。作者维护的是一个带 YAML 清单的仓库，说明重度作者已经想要文件加 GUI，"GUI 是数据的视图"有需求。

## 3. 模块覆盖

| 运行时模块 | 五张卡里用到的 |
|---|---|
| `fragment`（文本、位置、条件） | 5/5 |
| `journal` / `history`（节点、视图、压缩） | 5/5；西西弗斯的编年史和青空理的正则折叠都是手工实现的日志折叠 |
| `card.ts` 决定性结算（菜单、骰子、种子） | 0/5；样本里没有任何骰子或种子 |
| `lore.ts` 分层门控文本 | 0/5；西西弗斯的四个真相最接近，但内容是模型在揭示时写的 |
| 读数性数字 | 2/5（西西弗斯、青空理），都是模型判断、边界用散文说；伴星是计数器的反例 |
| 带 `when` 的 fragment | 1/5（青空理的六段好感度文本） |
| 状态条件触发的指令 | 1/5（青空理的告白事件） |

README 说读数性卡是生态里最常见的，五张里两张是。

## 4. 文本的六种

| 种类 | 卡 | 本项目今天的槽 | 缺口 |
|---|---|---|---|
| 关于角色与世界的知识 | 1、2、3 | fragment | 无 |
| 示范：正史的（第 0 轮） | 1；4 由模板生成 | 节点 | 第 0 轮的四种形状未定 |
| 示范：非正史的（example） | 1；5 的对白条 | 无 | 需要"紧挨历史之前、同一种语言、不进正史、不折叠"的槽 |
| 指令：框架、规则，含伪装成虚构的指令（旁白、读书摘录、标题） | 1、2、3、4 | fragment；规则走 check | 伪装的指令不可提取，也不应提取 |
| 受门控的知识 | 4（内容由模型写） | lore | 门控需求出现时形状不是固定分层文本 |
| 作者对玩家的话 | 1、5 | 无 | 无槽 |
| 生成器规则与状态 schema | 4、5 | card.ts（平标量） | 嵌套、动态记录、模型书写的文本字段；5 的 schema 是自然语言说明 |

## 5. 跨卡的规则

- **顺序是意义，缓存只在作者沉默处优化。** 三次出现：灰色と青的序列是论证；`head()` 后移带 `when` 的片段会脱离作者位置；西西弗斯把模板放尾部要近因。
- **读生态卡的分类规则。** `constant` 进 fragment；有键的才是 lore 候选；`extensions` 看变量框架；其余元数据。
- **不从散文和示范里提取规则。** 三张卡的编译输出是按作者顺序的 fragment，没有结构。"作者不写逻辑"同时意味着"作者不必写结构"和"运行时不替作者写语文"。
- **卡不等于角色。** 两张的 `name` 是作品名，一张两个人物，一张是生成器。`{{char}}` 是预设的宏泄漏进了卡，harness 里没有它的工作；头区第三层其实是"内容"。`{{user}}` 保留，只做名字替换。
- **玩家有时由卡来写。** 第二张写死了玩家；西西弗斯用表单向玩家要输入。槽位冲突按卡决定、作者可标记；卡声明的玩家输入是新东西。
- **第 0 轮有四种形状。** 作者用玩家第一人称写的正文；缺席、以反复句为事实上的开场；缺席、角色分配留给玩家；由模板插表单值生成。
- **秘密可以不门控。** 第二张把反讽直接交给叙事者，第三张靠序列揭示；西西弗斯的门控由代码记 `已揭示`、内容由模型写。支持"默认只做闸门和机会"，也说明门控需求出现时不是固定分层文本。
- **模型生成的可选项。** 西西弗斯每轮由模型写菜单、玩家选。与 `card.ts` 作者定义、`when` 门控的动作相反，是新形状。
- **harness 会伤卡。** 静止卡上的 record 与压缩；过去的结构化块进历史；ST 先丢示范。结构化阶段 opt-in 的立场被验证；纯聊天卡需要温和的 record。
- **卡是数据意味着玩家不需要别的。** 西西弗斯是一个 URL。

## 6. 对 README 第五节的触及

只是证据触及了哪些条目，不是改优先级。

1. 读数性状态：两张状态卡（西西弗斯、青空理）都在写之后更新，`<UpdateVariable>` 在回复尾部；青空理还要求有界步进并按阈值切文本；伴星是计数器的反例。
2. 输入驱动的窗口：第二、三张只用散文就做到了。
3. 玩家直接改正文：样本里没有证据。
7. 开放阶段：西西弗斯的模型写菜单是另一个问题，不是工具选择。

不在列表上但被暴露的缺口：示范的槽、作者对玩家的槽、第 0 轮的形状、嵌套与文本值的状态。
