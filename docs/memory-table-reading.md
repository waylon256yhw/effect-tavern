# 读表记录：龙血玄黄·数据库（shujuku），记忆表格与它之外长出来的东西

2026-10-18。读了 AlbusKen/shujuku（commit 4b311a6，2026-10-17）。它是 SillyTavern 的扩展兼 userscript，社区叫"数据库"或"记忆表格"，解决的是长程游玩里记忆与重大事件的追踪。前几份记录读的是卡与预设，它们把酒馆当作角色卡的运行时；这份材料不同，它把酒馆当作一个全能 AI 交互应用的宿主，在上面长出了记忆之外的一整套东西。

方法同前：对每个机制问"去掉它，分阶段回合模型里什么会坏"。坏的是需求，没坏的是补丁。这一份多问一句：**这个机制是为了补 ST 的哪个缺位**。前一份记录定了三个缺位（消息是字串、状态没有主人、请求形状不可编程）；这份材料暴露了第四个：**回合没有阶段**。ST 的一轮只有"整个提示词 → 整条回复"，任何"在固定点向模型要一样东西"的需求都只能做成一个异步钩子，自带提示词、自带调度、自带存储、自带与主生成的竞态处理。这个扩展的大部分体量就是这些钩子各自的四件套。

第 0 节是事后补的。第 1 到 5 节按机制逐条对照，这种读法有一个陷阱：对着别人长出来的形状一一对照，最后得出一张"我们缺什么"的清单，等于让补丁的形状决定协议。所以先站高一点，用三个问题把整份材料分成三堆，再决定下面的逐条对照里哪些值得当真。

## 0. 站高一点：三个问题

三个问题：哪些是对屎山的兼容补丁；哪些是一拍脑袋 vibe 出来、与任何工程实践不着调的；哪些我们已经有了更好、更健壮的形态。先给一个参照，再分堆。

### 0.1 参照：记忆系统这九个月往哪走了

同期的 agent 记忆框架 memU（NevaMind-AI/memU，2026-10-16 最新 commit）留了一条完整的 ADR 轨迹，是这个问题最好的对照组：

| 时间 | memU 的形状 | 记忆系统里"想"的部分 |
|---|---|---|
| 2025-11 到 2026-01（0.3 到 1.2） | memory item / category，LLM 分类、意图路由、充分性检查、RAG 摘要 | 全在记忆系统里：提取、归类、路由、判断够不够都是它调模型 |
| 2026-01 到 03（1.3 到 1.5） | "文件系统即记忆"：MEMORY.md、SKILL.md、INDEX.md | 开始往外移：输出是人能读的 markdown |
| 2026-06-30，ADR 0006 | 技能升为一等行，`track` 列 | 还在系统里 |
| 2026-07-01，ADR 0007 | 三条独立线，**去掉图、去掉实体索引、去掉多跳**，检索只剩 embedding 加 BM25 一遍过 | 检索侧的"聪明"全部删除 |
| 2026-07-07，ADR 0008 | **轨迹是唯一来源**：agent 自己的会话记录就是原料，三条线是三种提取 | 提取侧的"聪明"交给宿主 agent |
| 2026-07-23 以后（2.0.0-beta.0，之后再无 release） | README："The judgment and synthesis stay inside the agent. MemoryService makes no LLM or chat calls; it stores, embeds, and retrieves the skill Markdown the agent prepared." 核心 500 行 | 零。记忆系统 = 一个文件夹 + 一个 embedding 索引 + 宿主指令文件里一句"回答前先 retrieve" |

它的终态是：**agent 自己写自己的记忆（markdown），系统只存、只索引、只在固定点递回去**。所有曾经在记忆系统里的智力（分类、路由、图、多跳、充分性判断）九个月内全部删掉，不是因为做不好，是因为宿主 agent 做得更好。然后这个项目本身也停了：模型再强一步，连"回答前先 retrieve"都在变成宿主自己的事。

这是读 shujuku 的尺子。shujuku 是 2025 年末那个形状（记忆系统自己调模型做提取、分类、召回、再分类）在 AIRP 里的本地版，而且它的宿主连接缝都没有，所以每一层智力都得连带造一遍宿主该有的东西。memU 用九个月把那个形状删到 500 行；shujuku 沿原方向长到 24.5 万行。

### 0.2 第一堆：对屎山的兼容补丁

去掉 ST，这些东西没有一个有存在理由。

- 状态挂在消息上，于是有每楼一帧、checkpoint 加 log 回放、八种 checkpoint 原因、compaction、删楼 vault（宿主先 splice 后通知）、1.2 秒防抖窗口里"接受并记录"的竞态、隔离键、锁从下标改身份、种子行污染迁移、模板与数据 reconciler、SPV79 过渡检查点。表目录 50 个文件里约 35 个。
- 进提示词只能走世界书，于是有导出配置二十个旋钮、四组 depth / order 坐标、按行拆条目、关键词列、索引条目、"蓝灯"（选中的行本轮启用）、剧情推进输出编码再让扫描器去撞。
- 消息是字串，于是模型把 SQL 写进正文、正则抽 `<tableEdit>`、三种载体、HTML 注释兜底、"取最后一对"开关、原生工具默认关（"部分渠道收到 tools 字段会直接报错"）。
- 请求形状不可编程，于是有第四种模板语言（`<if seed|cell|cond|db|sql>`、`{[db...]}`、random / calc / max / min）和填表提示词里的越狱段、假 assistant 应答、尾部假 thinking。
- 零层：拦截宿主的 fetch，在 `chat[0]` 的一个字段里重建一棵回合树（分支、桥接、检查点、退出）。它就是"ST 没有日志树"这一句话的 425 KB 版。
- `callAI` 代理、`_ACU` 后缀、API 预设管理：全是在别人的全局命名空间里做客的代价。

### 0.3 第二堆：vibe 出来的，与工程实践不着调

去掉 ST 这些东西也不该存在，它们是方向错误，不是环境所迫。

- **"数据库"是 cosplay。** 真数据库的理由（并发写、即席查询、跨表完整性、多客户端）这里一个都没有：只有一个写者（填表 AI），读者拿到的是整表 dump 成的文本，唯一的查询消费者是模板里的 `{[db...]}`。用到的只有 CHECK 约束，那是 schema 校验，不是数据库。让模型写 SQL DML 再在浏览器里的 sql.js 上跑、失败重试，比让它按 schema 输出 JSON 多了一整个解析器和一整类错误。
- **纪要表每轮 ≥300 字是第二份转录稿，不是记忆。** 它和聊天线性同步增长，是复制，不是压缩。之后的四层机器（索引条目、召回模型选编码、编码当关键词、向量加 BM25 加 rerank）加飞行模式的大总结，全是在撤销"复制一份"这个决定。工程实践是分层摘要加对原文的检索，不是先复制再对复制品建索引再压缩复制品。
- **召回是个分类器，却做成了自由文本加扫描器。** 剧情推进让模型输出 AM 编码加括号理由，再强制"supplement 6 到 8 条背景设定"（HARD GATE、全大写、"绝对禁止"六条），下游靠关键词扫描激活。补充那 6 到 8 条是让模型抄一遍头区已有的内容。
- **时间让模型算**（`cur = prev + elapsed`，GLOB 兜格式，note 写公式），会漂。
- **13 个 agent 装在浏览器 userscript 里。** 续写 7 个、推演 6 个，自带 handoff summarizer、history compactor、token budget、run cache、read gate、evidence registry、final request token gate。这是在最不合适的地方重写一个 agent 运行时，没有持久执行、没有评测、没有可观测性，agent 数量本身当作功能。
- **代码体量与质量。** 24.5 万行、11 个测试文件；323 KB 的单文件编排器、234 KB 的持久化、162 KB 的 chat-service；文件名如 `manual-catch-up-provisional-bridge`（五态状态机）、`spv79-transition-checkpoint`；`merge-logic.ts` 头部写明"已遗弃·封存"及其永远不可能工作的原因，代码保留。AGENTS.md 与 `.cursor/rules/BajieAsk.mdc` 说明它是 agent 写、人授权发布的（"助手明确授权发布后，直接……提交和推送到 main"）。每个 bug 长成一个模块，是 vibe-coding 的典型病理。
- 桌宠讲笑话。

### 0.5 分堆之后剩下什么

把三堆拿掉，材料里剩下的真东西只有两件，而且都已经在 memU 的终态里：

1. **模型在固定点写自己的记忆，harness 只存、只递回。** 这就是 record 阶段的 notes 与产物。memU 的"agent 自己写 markdown，系统不调模型"与本项目"LLM 只做判断、渲染、提取三件事；代码掌握循环"是同一个立场，从两头走到一处。
2. **两层：钩子常驻，正文按需。** shujuku 的索引条目加正文条目，memU 的 L2 切片（embed 单元）滚上 L1 文档，本项目的 lore `layers[0]` 加正文层，是同一个结构。模型写的记忆行能和作者写的 lore 走同一条 lookup 路径，是这份材料里唯一值得采纳的新连接，而它只是把已有的两样东西接上，不是新机制。

还有一个背景量：上下文到了 1M 这个量级之后，一局几百回合的 AIRP 原文本身放得下。harness 的工作是成本（缓存前缀）与远处的质量（折叠），不是检索。检索只在几千回合的长篇上才成为问题，到那时也是 memU 已经收敛到的那一种（embedding 加 BM25 一遍过，无图无多跳），作为 lookup 阶段的插件实现。

对 §6 的影响：原先按对照写出的追加项里，`key` / `ops`（表收操作不收全值）是真实的工程取舍（diff 还是快照），但它是规模到了才需要的 ceiling，不是现在；`every`、`show` 是省钱旋钮，ceiling；"纪要作为默认产物"是第二堆里那个错误，删；只有 `recall`（模型写的行进 lookup）与"不开回合的 record"（导入旧文本）留下。§6 已按此重写。

## 2. 记忆表格本体：五个环节

记忆表格是一条流水线：**模板 → 填表 → 存储 → 注入 → 召回**。每个环节逐个看。

### 2.1 模板

默认八张表：全局数据（地点、时间、上轮时间、经过的时间，"有且仅有一行"）、主角信息、重要角色（姓名 UNIQUE、性别年龄、一句话介绍、外貌、持有物品、是否离场、过往经历 ≤300 字）、主角技能、背包（物品名 UNIQUE、数量 CHECK > 0、描述、类别）、任务与事件（任务名 UNIQUE、类型 CHECK IN 主线/支线）、纪要（时间跨度 GLOB 格式、地点、纪要 ≥300 字、概要 ≤30 字、编码索引 AMxxxx UNIQUE）、选项（四个选项，"有且仅有一行"）。另有一套"恋爱特化"覆盖，同名表换列。

每张表的声明是：一段 DDL（`CREATE TABLE`，列带 SQL 注释作为中文表头，CHECK / UNIQUE / NOT NULL 作为约束）、一段 note（每列的填写说明）、四段 initNode / insertNode / updateNode / deleteNode（什么时候做什么，附 SQL 示例，"禁止删除"也写在这里）、updateConfig（五个调度旋钮）、exportConfig（约二十个注入旋钮，见 2.4）。

| 机制 | 去掉后坏的 | 本项目的形状 |
|---|---|---|
| DDL 的列与类型 | 提取物有结构 | `products` 的 `shape`，列类型 text / int / boolean / enum |
| UNIQUE 列 | 行有身份，能被更新与删除 | table 形状的 `key` 列（见 §5） |
| CHECK GLOB 时间格式 | 时间可比 | 列类型；时间本身是 card.ts 已列的 ceiling |
| CHECK IN (...) | 离散值 | enum 列 |
| "有且仅有一行" | 单例 | record 形状 |
| note 的每列说明 | 模型知道怎么填 | 产物的问法（`text`），按 id 可覆盖 |
| "禁止删除 / 禁止操作" | 作者限制模型能做什么 | 产物上允许的操作集合，数据（见 §5） |
| 恋爱特化覆盖 | 不同题材不同表 | 模板卡自带的默认产物；玩家层只碰开关 |

### 2.2 填表

主生成结束后，另起一次模型调用（独立的 API 预设，可以是便宜模型）。提示词六段：越狱式开场、背景设定（`$U` 用户、`$C` 角色、`$4` 世界书）、正文（`$1`，上轮）、填表 AI 的规则、当前表格数据（`$0`，每张表的 DDL 加当前行）、尾部的假 assistant 消息。模型的输出是 SQL：INSERT / UPDATE / DELETE，禁止 DDL 与事务语句，禁止写 row_id。三种输出载体：正文里的 `<tableEdit>` 块（正则抽，带"取最后一对"开关、HTML 注释兜底、`insertRow(...)` 旧语法兜底）、strict JSON、原生工具调用（默认关，"部分渠道收到 tools 字段会直接报错而不会降级"）。解析失败按 `table-fill-retry` 重试。

填表前把表投影给模型：纪要表只给最后 10 行（固定），其余表按 `sendLatestRows`。隐藏列、锁定行列、飞行模式隐藏行在这一步剔除。

调度（`update-scheduler`、`update-orchestrator` 323 KB、`manual-catch-up-provisional-bridge`）：每表独立的 updateFrequency / batchSize / skipFloors / contextDepth，按 groupId 分组合并请求；"追平"把历史楼层按波次补填；追平范围跨过现有 full checkpoint 时走"临时锚点桥"，有五态状态机。

| 机制 | 去掉后坏的 | 本项目的形状 |
|---|---|---|
| 主生成后另一次调用，另一个模型 | 提取不占叙事者的输出，可用便宜模型 | record 阶段；阶段绑定连接是 harness 配置 |
| 模型写 SQL delta 而不是全表 | 几十行的实体表每轮全量重写既贵又丢 | 带 `key` 的 table 产物收操作而不是全值（见 §5） |
| 三种输出载体、正则抽取、兜底、重试 | 无 | 结构化输出，schema 即格式 |
| 越狱开场、假 assistant 消息、"主人的意志" | 无 | 不存在。填表是数据提取，不该需要越狱 |
| 纪要表只给最后 10 行 | 提示词不随纪要无限涨 | feed 产物回喂的窗口是产物上的一个数（见 §5） |
| updateFrequency / batchSize / skipFloors / 分组 | 省调用 | 省调用是真的；"每 n 轮提取一次"是产物上的一个可选数，默认每轮 |
| 追平、波次、临时锚点桥、boundary staging | 填表是异步任务，与聊天竞态；楼层可能漏填 | 不存在。record 是回合的一个阶段，节点要么有产物要么没有这一轮 |
| contextDepth | 填表看几楼 | record 看本轮正文加 Known；要看更多是 Known 窗口 |

### 2.3 存储

表数据挂在聊天消息上（`TavernDB_ACU_*` 字段），按隔离键（一个聊天多套表）分桶。V2 存储帧：每个楼层一帧，帧里是 full checkpoint（整份表数据，`reason` 有 init / periodic / manual / schema_change / compaction / import / migration / integrity_repair 八种）或 logEntries（本楼的变更操作，带 seq、source、baseRevision / commitRevision、writeSet）。当前表 = 从最近的 full checkpoint 回放 logEntries。SQLite 与消息字段双向同步（`sync-bridge`，加载方向 消息 → mergeAll → JSON → SQLite，保存方向反过来）。

围绕"状态挂在消息上"长出来的：删楼守卫（宿主在 splice 之后才发 MESSAGE_DELETED，被删楼层上的 checkpoint 已经没了，所以维护一个按对象引用判存活的影子 vault，在删除后把丢失的 checkpoint 嫁接到后继楼层）、1.2 秒防抖窗口内的残余竞态（文档里写"接受并记录"）、compaction（帧太多时滚动新 checkpoint）、锁的 v2（旧锁按行列下标存，插行后漂移，改为按 row_id 与列名）、稳定 row_id 分配器、种子行污染诊断与迁移、规范行归一化、模板与数据的 reconciler、schema 迁移 preflight、V2 恢复服务、SPV79 过渡检查点。表目录 50 个文件里约 35 个是这一类。

| 机制 | 去掉后坏的 | 本项目的形状 |
|---|---|---|
| 每楼一帧，checkpoint + log 回放 | 表状态能跟着楼层回退、swipe、删除 | 日志树折叠。节点存产物（模型输出），状态是折叠结果 |
| 删楼守卫与影子 vault | 宿主先删后通知 | 不存在。节点归 harness，没有"宿主" |
| 隔离键 | 一个聊天多套表 | 节点上的产物按 id 分，不需要第二个维度 |
| 锁按身份不按下标 | 玩家钉住某行某列 | 玩家对节点的动作"钉住"，记在节点上，按 key 不按下标（§5） |
| SQLite 双向同步 | 让模型能写 SQL、让模板能查 SQL | 不存在。SQL 是载体不是需求 |
| 模板与数据的 reconciler、迁移、污染修复 | 模板改了旧数据还在 | 卡版本（card-reading-2 §8 第 6 条）；旧节点按旧形状读，这是版本问题，不是运行时问题 |

### 2.4 注入

表进入主提示词的唯一通道是世界书。每张表的 exportConfig 决定：是否导出、是否按行拆成多个条目、条目类型（constant 常驻 / keyword 关键词触发）、关键词取哪一列、注入模板（`<记忆回溯>$1</记忆回溯>`）、是否另导出一个"索引条目"（选几列，每列 index_only 或 both）、四组放置坐标（entryPlacement / extraIndexPlacement / fixedEntryPlacement / fixedIndexPlacement，各有 position / depth / order）。

默认的纪要表就是这样做成两层的：每行一个条目，关键词是该行的编码索引 AMxxxx，正文是整段纪要；另一个常驻索引条目列出所有行的概要加编码。重要角色表同理：每行一条目，关键词是姓名，索引列出姓名加一句话介绍。其他表整表常驻。

提示词文本里还有第四种模板语言：`<if seed="战斗&主角">`（关键词命中最新输入与回复）、`<if cell=...>`、`<if cond=...>`、`<if db=...>`、`<if sql=...>`，支持 else 与十层嵌套；`{[db.表名.where("列","值").get("列")]}` ORM 风格查询与 `{[sql "SELECT ..."]}` 原生 SQL 兜底；`<random>`、`<calc>`、`<max>`、`<min>` 标签。

| 机制 | 去掉后坏的 | 本项目的形状 |
|---|---|---|
| 索引条目常驻，正文条目按关键词 | **两层记忆**：索引便宜常驻，正文按需 | lore 的 `layers[0]` 钩子与正文层。模型写的记忆与作者写的 lore 走同一条路（§5） |
| 关键词 = 编码索引 / 姓名 | 让扫描器能找到那一行 | 不需要扫描器。lookup 阶段的枚举就是索引 |
| 四组放置坐标 | 作者定先后与远近 | 回合装配的字段（"离回复近"）；顺序是文档顺序 |
| 整表常驻 | 当前状态在叙事者眼前 | feed 产物折叠后进 tail 的 `Current:` |
| `<if seed/cell/cond/db/sql>`、`{[db...]}`、random/calc | 按状态切说法、从表里取值 | `when` 读产物路径的 Cond；随机数不进提示词 |

### 2.5 召回

三级，可叠加：

1. **关键词扫描**（ST 原生）：模型在正文里提到 AM0012 或某个姓名，下一轮扫描器带出那一行。被动，靠模型自己念出编码。
2. **剧情推进**（这个扩展的）：主生成之前多一次模型调用，输入是背景设定、前三轮 AI 输出、纪要索引、本轮用户输入，要求输出两段：`<recall>` 从索引里选 20 条最相关的 AM 编码（每条括号写理由），`<supplement>` 从背景设定里"强制 6 到 8 条"相关设定。编码注进最终提示词的一段系统文字（"以下输入的代码为接下来剧情相关记忆条目的对应的索引编码"），扫描器据此激活那些行。
3. **交火模式**（向量）：纪要行按"概览 + 正文"做 embedding，BM25（中文按字与双字切）与余弦分做 RRF 融合，候选 200 条过 rerank，保留 30 条，minScore 0.35，选中行本轮切成"蓝灯"（启用的常驻条目）。rerank 没配或失败时 fail-closed。向量索引作为镜像随楼层帧存储，有自己的 flush 队列、GC、重建、对齐状态。

另有**飞行模式**：可见纪要达到 N（默认 15）条时，要求模型新增一行"大总结"归纳全部可见纪要（"不得只总结最新若干条、不得遗漏会改变整体脉络的事实"），然后隐藏这些纪要行；大总结表是按阶段追加、不可变的。旧的"自动合并纪要"功能已封存，文件头写明原因：SQLite 模式下提示词要 SQL、解析器只认 `insertRow`，必然失败。

| 机制 | 去掉后坏的 | 本项目的形状 |
|---|---|---|
| 剧情推进的 recall | 窗口外的记忆按相关性回来 | README 方向 2 的便宜分类器：lookup 阶段读本轮输入加近几轮简报，菜单是钩子，多选可空。纪要行的钩子就是它的概要 |
| recall 必须说明理由 | 防偷懒取连续记忆 | 结构化输出不需要理由字段；要防偷懒用枚举加上限 |
| `<supplement>` 强制 6 到 8 条设定 | 无 | 删。它让模型抄一遍头区已有的东西 |
| 向量 + BM25 + rerank | 索引大到枚举放不下 | README 方向 2 说的"真大就两跳"的第二跳；harness 插件，不是协议 |
| 蓝灯 | 选中的行本轮进提示词 | 本轮的 disclosure，记在节点 `read` 上，沿路径去重 |
| 飞行模式大总结 | 纪要太多时分层 | 压缩是派生视图，按块折叠已有。差别是他们让模型写、我们代码拼 notes；LLM 写的摘要是压缩策略的一个可选项，不是新机制 |
| 大总结不可变、按阶段追加 | 摘要稳定，缓存不炸 | `folded` 的块边界已是为此 |

## 3. 记忆之外长出来的

这些都不是记忆的需求，但都用同一个模式长出来：一个钩子、一套提示词、一份存储、一个调度器、一组与主生成的竞态处理。

| 功能 | 它在做什么 | 用本项目的词说 |
|---|---|---|
| 零层 | 拦截宿主生成请求，在 `chat[0]` 的一个字段里维护自己的回合时间线（floor、attempt、effect receipt），有分支、桥接、检查点、退出回宿主。七态 turn phase | 在 ST 里面重建一棵日志树。本项目的 journal 就是这个，不用拦截谁 |
| 智能续写 | 七个 agent 规划大纲（分 stage、分 turn，有 tempo 校验），维护者写"模块"，终审把关，然后替玩家往输入框发指令，驱动宿主生成；可设最多自动 stage 数、总时长 | 自动化的 aside 通道：一个导演在写玩家的 aside。按 README 方向 7，是 harness 插件的一种阶段类型，不是卡协议 |
| 格林推演 | 六个 agent 在每条回复后推演幕后世界，写账本（schema v6），引导撰写者产出"场外信号"按三组插进正文并重渲染 | 一个带自己账本的 director 阶段，产出是 narrate 的一段 tail。同上，插件 |
| 剧情推进的"任务" | 可配置的多步预生成任务，每步一个提示词组，`<if>` 控制 | 阶段配置。harness 的事 |
| 模板助手 | 自然语言描述 → LLM 产出表结构 diff（加表、删表、改列、改说明、改锁），标出高风险项（删表、改全局注入、改 schema），确认后应用 | **方向 4 的先例**：自然语言编译成数据，带 diff 与风险提示。这是这份材料里唯一与本项目同向的东西 |
| Agent 世界书接管 | agent 读世界书条目决定哪些"绿灯"进本轮，把条目"技能化"写元数据块 | lookup 阶段。它证明"模型选条目"这件事社区已在做，只是做在世界书的开关上 |
| 外部导入 | 把一本小说 TXT 分段喂给填表 AI，建出初始记忆 | 对一段文本跑 record 而不开回合。真需求，记一笔 |
| 正文优化、内容替换 | 对回复再调一次模型改写；按规则替换文本 | 不是记忆；也不在本项目的方向上 |
| `callAI` 代理 | 让别的插件借它的 API 配置调模型，不泄露密钥 | provider 层归 harness，插件拿不到密钥是自然的 |
| 桌宠、气泡、笑话、通知轮播 | 无 | 无 |

四个大功能（续写、推演、零层、向量）合计 4 MB，是记忆表格本体的两倍半。它们的共同前提是：**ST 不提供阶段，所以每个"在固定点向模型要一样东西"的功能都得自己做一遍回合**。本项目有阶段，这四个东西要么是一个阶段类型（续写、推演），要么根本不需要（零层），要么是一个阶段的可替换实现（向量召回）。

## 4. 从形状看：第四个缺位

| ST 的缺位 | 被迫长出的东西 | 本项目的结构决定 |
|---|---|---|
| 回合没有阶段 | 填表钩子、剧情推进钩子、推演钩子、续写钩子；每个自带提示词、调度、存储、竞态处理、重试；填表与主生成赛跑，于是有追平、波次、锚点桥 | 回合是固定骨架，record 是其中一个阶段；没有钩子 |
| 状态没有主人（再一次） | 表挂在消息上，每楼一帧，回放、compaction、删楼 vault、隔离键、锁按身份存、种子污染迁移 | 状态是日志树折叠的结果，节点归 harness |
| 消息是字串（再一次） | 模型写 SQL 到正文、正则抽 `<tableEdit>`、三种载体、HTML 注释兜底 | 结构化输出 |
| 请求形状不可编程（再一次） | 四组放置坐标、第四种模板语言、SQL 嵌进提示词文本 | 装配是代码；条件是 Cond |

## 5. 跨文件的规则

- **记忆是两层的，而且和 lore 是同一个东西。** 这份材料最有价值的一个形状：纪要表的索引条目常驻（概要加编码），正文条目按需（整段纪要）；重要角色表同理。这正是 lore 的 `layers[0]` 钩子与正文层，只是作者写的换成了模型写的。所以模型写的记忆与作者写的 lore 应走同一条路：lookup 阶段的枚举里既有 lore 的钩子也有记忆行的钩子（产物上指定哪一列是钩子），选中即 disclosure，记在节点 `read`，沿路径去重。README 方向 2 的分类器、这里的"剧情推进"、交火向量，是同一个 lookup 阶段的三级实现，前两级是协议，第三级是插件。
- **记忆条目是产物；表大了才收操作。** 实体表（角色、物品、任务）有身份：几十行、每行几百字，每轮让模型全量重写既贵又丢，这是他们选 SQL delta 的真实原因，不是 SQL 的功劳。本项目的 table 产物先收全值；量到了再加可选 `key` 列，答案变成操作 `{ upsert: Row[], delete: Key[] }`，代码施加，折叠即沿路径重放。操作词表封闭，与效果词表（set / add / event）是同一种东西；作者的"禁止删除"是产物上允许哪些操作的声明。按 §0 这是 ceiling。
- **回喂窗口是产物上的一个数。** 纪要表只回喂最后 10 行、其他表按 `sendLatestRows`：feed 产物的 `show` 是最近几项（list / table）；record 与 text 整份。不设则全给。
- **调度、回放、删楼守卫、隔离键、锁漂移在日志树里没有对象。** 它们全是"状态挂在消息上 + 填表异步于生成"的后果。要保留的只有一个真需求：省调用。产物上一个可选的"每 n 轮提取一次"（默认 1）覆盖它，而且因为 record 是阶段，跳过的那一轮节点上就是没有这个产物，不存在"漏填要追平"。
- **分层摘要是压缩策略，不是新机制。** 飞行模式的大总结 = 按块折叠的派生视图。他们让模型写一段，本项目代码拼 notes；若要 LLM 版，是 `compress` 的一个可选实现，输入是同一段区间的 notes 与送入的 lore，输出缓存按区间，与现在一致。
- **"钉住一行"是对节点的玩家动作。** 锁的 v2 把身份从下标改成 row_id 加列名，正是因为锁不该漂移。本项目里它与"钉住 lore"是同一个动作面（card-reading-2 §8 第 8 条）：对产物的某个 key 的某一列，记在节点上，record 不改它。
- **编译步骤已有先例。** 模板助手：自然语言改表 → diff → 高风险项 → 确认。方向 4 做的时候，输出该带 diff 与风险标注，这是社区已验证的交互形式。
- **时间是真需求，仍是 ceiling。** 全局数据表让模型做 `cur_time = prev + elapsed`，用 CHECK GLOB 兜格式，note 里写公式。它会漂。本项目先把它当 feed 的 record 产物（文本），代码算时间仍在 card.ts 的 ceilings 列表里不动。
- **越狱与假对话不该出现在数据提取里。** 填表提示词六段里三段是越狱开场、假 assistant 应答、尾部假 thinking。它们是请求形状不可编程时作者唯一能动的东西，和预设里那三成"替 harness 干活的文字"是同一类（preset-reading-2 §6）。

## 6. 对协议的要求

按 §0 的分堆重写。这份材料对协议的净贡献是两条，其余要么是 ceiling 要么不进。

**进协议的**

1. `products[].recall`：可选，指定一列为钩子。有它的产物，其沿路径累积的行进入 lookup 阶段的枚举，与 lore 的钩子并列；选中的行作为本轮 disclosure 送叙事者，记在节点 `read`，沿路径去重。节点 `read` 的 Disclosure 因此要能指向产物行（产物 id 加行序），不只是 lore id 加层。这是"模型写的记忆与作者写的 lore 同路"，把两样已有的东西接上。
2. 不开回合的 record：对一段外部文本（导入的小说、旧存档）分段跑 record，产物挂在一个没有输入与正文的根节点上。这是 memU 的"轨迹是来源"在这里的形状：原料可以不是本局产生的。

**ceiling，记下不做**

3. 带 `key` 的 table 产物收操作 `{ upsert, delete }` 而不收全值。diff 还是快照是真实的取舍，但只在表大到全量重写成本可见时才需要；先全值，量到了再加。
4. `every`（每 n 轮提取一次）、`show`（回喂取最近几项）：省钱旋钮，模型便宜到一定程度就不需要。
5. 枚举放不下时的两跳与向量检索：lookup 阶段的插件实现，形状按 memU 收敛后的那一种（embedding 加 BM25 一遍过，无图无多跳）。
6. 钉住产物的一行或一格：对节点的玩家动作之一，随 card-reading-2 §8 第 8 条一起定。

**删掉的**

7. "纪要作为默认产物"（每轮一段带时间地点的正文）。它是第二份转录稿，§0.3 的第二条。notes 保持短事实句，压缩走折叠。

**不进协议的**

8. 续写、推演是阶段类型，归 harness 插件面；零层不需要；正文优化、内容替换、桌宠不在方向上。
9. 调度、追平、锚点桥、删楼守卫、隔离键、锁、SQL、第四种模板语言、四组放置坐标、越狱段、`callAI`：§0.2 与 §0.3 两堆，没有对象。
