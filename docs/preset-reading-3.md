### 1.3 `Turing正文质检 v3.11`（生成后打磨管线）

内置在 `extensions.tavern_helper` 中的 60KB 脚本，实质是一个跑在浏览器端、挂接在 `MESSAGE_RECEIVED` 事件上的**生成后 polish 阶段**：

1. **剥壳**：先剔除 `<build>`、`<thinking>`、`<time>`、`<parallel_world>`、`<option>` 等块，只提取正文段落。
2. **本地三级确定性扫描**：
   - **Tier A（绝对禁用词）**：如 `生理性`、`灵魂`、`低笑`、`不由得`、`某种`、`像只...的兽/猫` 等。
   - **Tier B（句式结构正则）**：如 `不是A，而是B`、破折号解释句、段尾升华总结句、心理百分比分析、五感排比、动作链堆砌。
   - **Tier C（`FREQ_RULES` 千字密度阈值）**：按每千字出现次数判定是否超标——例如比喻词（`像/仿佛/宛如/好似`）上限 **3 次/千字**，口水词（`缓缓/轻轻/微微/淡淡`）上限 **5 次/千字**。未超阈值不触发，超出阈值才将对应句子标为命中。
3. **二次模型调用与 JSON Patch 原地拼接**：
   - 支持配置独立的质检 API 连接（URL / Key / Model），分 `hits`（仅针对本地扫描命中的句子修复）和 `full`（全文可读性润色）两档。
   - 要求质检模型输出 `【问题】` 与 `【补丁】[{"old":"原句","new":"改写句"}]`，脚本在落定消息上逐条 `replace` 写回 `mes.mes` 与 `mes.swipes`。

## 2. 三分法批判：技术债、作者 Vibe 与预设的真实边界

在看具体映射之前，先把立场摆清楚：**预设唯一不可替代的存在意义是 jailbreak（在我们的体系里即协议壳 `Hat`，`fragment.ts`），外加最基础的写作坐标定义（人称、转述、代劳边界、篇幅）。** 现在生态预设里连篇累牍的「语文工程」（教模型怎么写群像、怎么防超雄、怎么写潜台词），本质上都是在替孱弱的角色卡作者找补。语文问题就是卡与散文自身的问题，不应当沉淀为系统的结构复杂度。

用三分法切开这份预设：

### 2.1 第一堆：替酒馆负担的宿主技术债（Host Tech Debt）

这些机制之所以写成这样，完全是因为 SillyTavern 缺乏对应的原语：

1. **用 `{{setvar}}` / `{{getvar}}` 手搓跨阶段与同槽位编译器**：
   ST 的提示词条目是孤立的布尔块。作者为了让多个独立开关共同往同一个 `<ban>` 块里塞词，或者让打开 `#69 <对白强化>` 时自动往末尾 `#112 <build>` 思维链里塞一句自检题（`{{setvar::duibai::...}}`），只能拿宏变量当全局可变状态用。
2. **用正则按深度硬剥单字符串消息**：
   因为 ST 的消息只是一个大字符串，模型被迫在同一轮输出里先后吐出 `<build>` 思维链、正文、`<time>`、`<parallel_world>`、`<option>` 和小剧场，再靠 20 条正则在显示侧转成 `<details>` / 按钮 HTML、在 prompt 侧按 `minDepth: 0` 或 `minDepth: 2` 剥掉。
3. **把后处理阶段塞进 UI 脚本扩展**：
   ST 的回合只有一次生成调用，没有 `polish` 阶段。作者为了做生成后局部改写，只能在 `tavern_helper` 里写 60KB 的前端脚本，在 DOM 收到消息后自己调第二次 `fetch` 再改写楼层文本。

### 2.2 第二堆：预设作者自己 Vibe 出来的伪需求（Vibe Over-engineering）

这些东西没有任何标准化实践背书，甚至在机制上与注意力规律背道而驰：

1. **常驻上下文的长期追踪面板（`#80 <time>`、`#81 <parallel_world>`、`#92 恩仇榜`）**：
   这组面板对应的正则（Regex `#5`、`#6`）只做了前端 `<details>` 折叠，**`promptOnly` 为 `false`，意味着每一轮生成的日期、天气、服装、好感度、NPC 平行世界动态全都永久留在历史消息里发给模型**。
   这非但不是真正的「上下文连续性」，反而是典型的**附加产物未剥离导致的注意力涣散与 ICL 惯性**——每一轮都强迫叙事模型分神去填状态栏、编造不在场 NPC 的平行世界小作文，且历史里堆积的面板格式会形成强大的上下文重力，让模型越来越像填表机器。
2. **前置 7 步 `<build>` 思维链八股与配额查岗（`#112`）**：
   要求模型在写正文前先按固定八股完成 7 步检讨（甚至要求先列出 A/B/C/D 四个备选场景大纲再四选一、逐条核对词汇配额）。把后验检查硬塞成叙事者的前置作文题，直接稀释了写正文时的注意力。
3. **在系统提示词里堆砌 `<ban>` 负向清单（`#55–#59`）**：
   在头部和尾部反复罗列几十个禁用词与句式，犯了提示词工程最经典的「不要想粉红大象」错误——负向词表本身先把这些概念激活进了注意力区（这也是为什么作者自己最后不得不另写一套 `Turing正文质检` 脚本在生成后擦屁股）。

### 2.3 第三堆：`effect-tavern` 已有的更高阶形态

| 图灵预设的做法 | `effect-tavern` 的既有形态 | 为什么我们的形态更干净 |
|---|---|---|
| `#1–#17`、`#31` 伪造 `<context>` 与 `<thinking>` 破限壳 | `Hat`（`fragment.ts`：`narrate.head` / `narrate.tail` / `review.head`） | 绑在连接（Connection）上而非卡或规则包上；harness 自身零内置文本，彻底保持中性 |
| `#62–#68` 人称、防抢话、转述、篇幅 | `Writing`（`fragment.ts`：`pov`、`echo`、`agency`、`verbosity`） | 收敛为四个正交枚举/布尔开关，编译进 `pov` 与 `verbosity` 槽位，卡或玩家层可按同槽位规则自然覆盖或让位 |
| `#21` 大总结、`#80–#82` 状态栏与四选项、`#90–#109` 20 个小剧场 | `Product`（`product.ts`：`world` / `context` / `theater`）+ `Rules` / `Readout`（`card.ts`） | 产物按 `(feed \|\| recall)` × `fold` 正交分类；小剧场（`!feed && !recall`）走 `narrate` 的 `<<aside>>` 流式切分或 `demand` 按需生成，**天然不进 `prose(t)` 与转录稿**，零正则剥离 |
| `#112` 在 `<build>` 里夹带剧情方向规划与规则核对 | `session.ts` 的独立阶段：`direct` 与 `check` | 规划（`direct`）与核对（`check`）各自是独立阶段调用，不污染 `narrate` 的续写上下文，玩家也无需配置 CoT 剥离正则 |
| `Turing正文质检` 的死词扫描与局部替换 | `polish.ts`（`scan` → `marked` → `splice`） | 原生作为 `check` 后、`record` 前的条件阶段：代码确定性扫描引号外文本，只把命中句包进 `<target>` 交由模型单句重写再拼回正文 |

## 3. 核心追问：从「中性 Harness 的形态表达力」看，我们缺什么？

我们要做的不是一个预设，不是一张角色卡，不是一个制卡器，而是一个 **harness**。
harness 的根本要求只有两条：**绝对中性**（不内置任何文风品味、禁用词库或破限话术），以及**最高的、最抽象的表达力**（用最少、最正交的原语，让任何合理的机制诉求都能自然表达，而不必像在 ST 里那样靠宏变量和正则黑客绕路）。

照这个标准把内容细节与个人 vibe 全部筛除后，这份预设真正触碰到我们现有**形态表达力（formal expressive power）**边界的，只有以下 **3 个抽象原语问题**：

### 3.1 后处理（`polish.ts`）的检出与触发原语

我们的 `polish` 已经走对了大方向（把负向禁令从前置 prompt 移到后置代码扫描 + 局部句子重写），但当前 `Entry`（`polish.ts`）的形态原语过于狭窄：

1. **缺少「密度/阈值门控（Frequency / Threshold）」**：
   目前 `Entry`（`{ pattern, hint }`）只有「命中 1 次即触发重写」的零容忍模式。这只能处理绝对死词（如 `生理性`），却无法表达**「单次合法、高频才算病句」**的语言现象（如 `像`、`仿佛` 等比喻词，或 `微微`、`缓缓` 等副词，一轮出现一两次完全正常，密度超标才需要打磨）。没有阈值字段，这类规则在 `lexicon` 里根本无法落笔。
2. **缺少「引号作用域（Quote Scope）」控制**：
   `scan` 写死了 `maskQuotes`（一律忽略引号内文本及跨引号边界）。如果一条打磨规则针对的恰恰是台词腔调或跨引号的对话标签句式（如 `」他说，「`），当前扫描器在形态上无法表达。
3. **缺少节点上的「按需打磨（On-demand Polish）」触发器**：
   `Product` 既有随轮自动执行（`on: true`），也有在已落定节点上按需触发的 `demand` 动作；而 `polish` 目前只能绑死在回合流水线里自动跑，节点动作 `edit` 又只接收玩家手改完的纯文本，缺少对单个既有节点按需触发（或指定提示词触发）局部打磨的动作原语。

### 3.2 玩家层（`Layer`）的组合语义与条目开关粒度

在 `fragment.ts` 与 `layer.ts` 中，玩家层合并有两个形态上的局促点：

1. **多个玩家层（Packs）之间的同槽位 `mode: "both"` 无法叠加**：
   `resolve`（`layer.ts`）用单值 `Map<string, Item<Fragment>>`（`slots`）收集所有玩家层的片段。`mode: "both"` 目前只保证了「最后一个赢下该槽位的玩家层」不覆盖 `card.frame`；但如果玩家同时挂载了两个都针对 `style` 槽位声明 `mode: "both"` 的 Pack（或 `overlay` + `pack` + `local`），后一个玩家层执行 `slots.set("style", ...)` 时仍会直接覆盖前一个玩家层的同槽位片段。
2. **层内列表原语缺少独立开关与标识**：
   `Layer` 中，`fragments` 有 `id` 与 `enabled`，`products` 有 `id` 与 `on`；但 `lexicon`（`Entry`）与 `entries`（`PackEntry`）没有 `enabled` 开关（`lexicon` 甚至没有 `id`）。玩家挂载一个规则包后，无法在 `local` 层像关掉单条 `fragment` 那样单独关掉包里的某条词表规则。

### 3.3 回合/通道原语：带上下文的纯场外探讨（Ephemeral / Meta Query）

在 `session.ts` 中，`act` 与 `note` 两个通道驱动的都是完整的故事回合（戴 `narrate` 续写帽生成故事正文 → `check` → `polish` → `record` 记账，并在日志树上落定一个故事节点）。
当玩家想基于当前完整故事上下文，与模型做一次**不推进故事、不写正文、不触发 `record` 记账的纯场外探讨**（对应预设 `#116 和图灵聊天`）时，目前只能借用一次性 `demand` 产物，或在日志树上分叉再丢弃。这是否需要一个独立的轻量动作原语，还是继续交由 `demand` 承担，是通道层唯一剩下的边界问题。
