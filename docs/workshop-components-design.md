## 1. 背景与问题诊断：为什么固定 Tab 表单走不通？

在 Phase 2 后端（`checkCard` `empty-text` 门禁、`compile` / `sort` / `review` 三个闭词表纯函数接口、以及 `/api/cards/:id/draft` 草稿持久化）落地前后，我们尝试了三版基于固定分栏或固定顶栏 Tab（`设定 / 正文 / 暗线 / 规则`）的前端原型，均宣告失败。

复盘原因，核心症结在于：**把底层运行时装配结构（Runtime `Card` Schema）直接当成了作者侧的创作分类（Authoring Taxonomy）。**

1. **`Card.frame` 是覆盖协议，不是逼作者填表的旧酒馆冗余字段**
   - 在 [`packages/runtime/src/card.ts`](../packages/runtime/src/card.ts) 与 [`packages/runtime/src/layer.ts`](../packages/runtime/src/layer.ts) 中，`frame` 的 7 个槽位（`persona / pov / voice / style / setting / language / verbosity`）存在的唯一工程理由，是与玩家全局的 `Writing` 偏好层做按槽合并与让位（`Fragment.mode: "yield"`，`layer.ts` 的 `resolve`）。
   - 如果在 UI 上把它们画成常驻表单，就会立刻退化成 SillyTavern V2 时代为了迎合早期 ERP 与提示词魔咒而拍脑门定下的冗余格子（`Scenario`、`Personality`、`Mes_Example`）。绝大多数卡片根本不需要填满这 7 个槽。
2. **`Card.fiction: Fragment[]` 是装配切片数组，不是让作者在文本框里手搓伪 YAML**
   - Runtime 把 `fiction` 设计为 `Fragment[]`（[`packages/runtime/src/fragment.ts`](../packages/runtime/src/fragment.ts)），只是为了让不同段落能按文档顺序拼接，或挂载 `when: Cond` 在好感度/状态变化时整段进出。
   - 在现有迁移卡（如 [`banxing.yaml`](../packages/runtime/cards/banxing.yaml)、[`ri.yaml`](../packages/runtime/cards/ri.yaml)）中，`fiction[].text` 里之所以塞满了手写的缩进伪 YAML（`姓名: 依瑞丝`、`核心特质:`），纯粹是因为旧酒馆只有一个大号纯文本框，作者被迫用纯文本模拟结构化角色表。解法不是再造一个键值表单，而是让这些块按 `label` 拆成几段散文（《盐道》的「官府与盐帮」「眼下」就是这个形状）；导入卡的键值块先原样放进 `[自由正文段]`，作者下次修订时改写。正文槽从此只有散文与 Markdown。
3. **生态中的卡片形态跨度极大，不存在一套所有卡通用的常驻标签页**
   - 有的卡是纯粹的散文（《公共妓女》），有的卡是无主角的碎片档案集（《灰色と青》），有的卡是单人角色加开场白（《伴星》），有的卡是好感度阶段驱动的恋爱剧（《圣女莉莉》），有的卡则是无固定人设、纯靠数值与世界账本运转的机制沙盒。
   - 把 `设定 / 正文 / 暗线 / 规则` 全部常驻在顶栏，会让纯散文卡显得臃肿，让机制卡的各个耦合面（变量定义、阶段描写、回合后判据）被拆散在不同 Tab 里。

## 2. 核心架构：两层结构 —— 有界二维胶囊画布 + 组件专属内页

Workshop 前端放弃「固定顶栏 Tab」，采用经 [`docs/workshop-prototype.html`](./workshop-prototype.html) 验证定稿的**两层架构**：
- **第一层（宏观总览层）**是一张**不产生外层滚动的有界二维胶囊画布**，只回答「这张卡由哪几个组件拼成、各占多少权重与上下文预算」；
- **第二层（组件详情层）**是**每类组件一页的专属整页编辑器**（不塞进局促的弹窗），按组件内容量身定做版式。

### 2.1 第一层：有界二维胶囊画布（Bounded 2D Capsule Canvas）

- **唯一语义落点（Singleton per Component Type，最多 7 个）**：
  - 7 类组件在画布顶层各自最多挂载 **1 次**。同类内容的复数条目（如多篇常驻设定章节、多个开场、多条词条/暗线、多个状态字段）全部收敛在对应组件内部，杜绝把画布堆成十几个散乱碎块。
- **二维比例网格与拖拽重排**：
  - 桌面端画布由若干行（`rows`，按高度分数 `h` 分配）与行内若干胶囊块（`items`，按宽度分数 `w` 分配）瓜分；相邻缝隙（`.gx` / `.gy`）支持拖拽调节比例（单侧夹紧在 `12%–88%` 之间，双击缝隙恢复均分）；手机端（`< 72rem`）自动坍缩为单列。
  - 拖拽任意胶囊块至另一胶囊块上时，按落点位置显式提示五种重排热区：**交换位置（swap）**、**并排放在左侧（left）**、**并排放在右侧（right）**、**放到上方新的一行（top）**、**放到下方新的一行（bottom）**。
- **四档面积驱动的语义缩放（4-Tier Semantic Zoom via `ResizeObserver`）**：
  - 每个组件声明四档尺寸下的渲染契约，由画布当前分配给该胶囊的像素宽高自动决定呈现哪一档，使同一组件在角落里是一枚紧凑药丸，获得空间时自动展开为结构可视化图：
    1. **`xs`（胶囊）**：高 `< 92px` 或宽 `< 150px` 时坍缩为单行药丸（组件符号 + 标题 + 核心计数）；
    2. **`s`（指标）**：标题栏 + 大字号等宽核心指标（如章节数、字数、阶段数、词条数）；
    3. **`m`（摘要）**：指标 + 内部条目摘要列表（底部渐变遮罩）；
    4. **`l`（结构图，宽 `≥ 380px` 且高 `≥ 250px`）**：替换为该组件专属的**结构可视化图**（如设定文稿的章节字数比例条与首章摘录、状态的灰阶分段尺与每回合判据、暗线的阶梯解锁链、检定的成功率条与终局条件、护栏的三栏概览等）。
  - 每个胶囊底部常驻该组件的 Token 估算值。
- **顶栏区域**：
  - 左侧：卡片名、组件数与总 Token 估算、一句话简介（`summary`）原位编辑。
  - 右侧：草稿自动保存状态与「保存入库（转正）」按钮（受 `empty-text` 门禁控制）、「导入原稿分拣（`sort`）」入口、「切片预览与检查」抽屉、「均分」与「添加组件」按钮。
- **直观区分卡片原型**：点进不同卡片时，二维画布呈现的胶囊组合截然不同，一眼就能看清这张卡的性格：

| 生态典型卡 | 卡片形态特征 | 画布上挂载的组件胶囊（最多 7 类，每类唯一落点） |
| :--- | :--- | :--- |
| **《公共妓女》**<br>（[`card-reading.md`](./card-reading.md) 案例，仓库内无 YAML） | 纯散文、无特定主角、无开场、无数值 | 1. `[设定文稿]`（单胶囊满幅铺满整张画布） |
| **《灰色と青》**<br>（[`card-reading.md`](./card-reading.md) 案例，仓库内无 YAML） | 多篇档案设定集（重构后区分常驻基底与按需概念） | 1. `[设定文稿]`（收纳真正每轮常驻的基础篇章）<br>2. `[暗线与词条]`（通过章节底栏「移入暗线与词条 ↗」，将“容器理论”等易造成刻板印象的抽象段落剥离为按需调取条目） |
| **《伴星》**<br>（[`banxing.yaml`](../packages/runtime/cards/banxing.yaml)） | 传统单人角色卡（固定人设 + 开场白） | 1. `[设定文稿：依瑞丝]`（导入时为键值块，改写后为内部按章节组织的散文）<br>2. `[开场与视角]`（单开场 + 剧内角色通道 + 玩家关系一句话） |
| **《圣女莉莉（理）》**<br>（[`ri.yaml`](../packages/runtime/cards/ri.yaml)） | 好感度阶段卡（多角色 + 6 档阶段 + 隐藏心事 + 多开场） | 1. `[设定文稿]`（莉莉 / 罗伦斯分章散文）<br>2. `[状态与阶段]`（好感度 0–100 分段尺 + 阶段散文 + 每回合升降判据）<br>3. `[暗线与词条]`（告白心事阶梯暗线 + 单层词条）<br>4. `[开场与视角]`（3 个并排开场，含第 3 支 IF 线初始好感度覆写） |
| **《盐道》 / 《竹林》**<br>（[`yandao.yaml`](../packages/runtime/cards/yandao.yaml)、[`wuxia.yaml`](../packages/runtime/cards/wuxia.yaml)） | 机制与世界驱动（按需词条库、动作检定、世界账本、事后护栏） | 1. `[设定文稿]`（世界与人物基底）<br>2. `[暗线与词条]`<br>3. `[状态与阶段]`<br>4. `[行动与检定]`<br>5. `[小剧场与世界账本]`<br>6. `[事后护栏与禁词]`<br>7. `[开场与视角]` |

### 2.2 第二层：组件专属整页内页（Layer 2: One Page per Component）

- **整页层级（非弹窗）**：点击第一层任意胶囊块，通过视图过渡（生产环境使用原生 `View Transitions API`）进入铺满舞台容器的该组件专属内页；按 `Esc` 或点击左上角「‹ 总览」退回第一层画布。
- **顶栏微缩导航图（`.minimap`）**：第二层顶栏紧邻「‹ 总览」右侧，绘制一枚等比例映射当前卡片第一层二维胶囊排布的微缩网格图，高亮当前所在组件；点击任意小格即可直接切换到对应组件内页，无需先退回总览页。
- **一组件一版式**：不搞千篇一律的通用表单，每个组件内页采用最契合其内容结构的专属版式（章节目录+文稿纸、左视角栏+横向开场卡列、分组列表+阶梯预演、分段尺+阶段散文+双向判据条、检定表+实时试掷、小剧场+世界账本分栏、护栏三栏清单与试审沙盒）。

## 3. Runtime 表现力与 7 类可选组件的完整映射

为确保组件形态完整且不丢失底层 Harness 的任何能力，我们将 [`packages/runtime/src/`](../packages/runtime/src/) 的全部表现力梳理为 **四大组、7 类可选组件**（每类组件在画布上唯一落点）：

### A 组：叙事基底（Head & Node 0）

#### 组件 1：`[设定文稿]`（`prose` — Always-On Chapters）
- **创作定位**：一切每轮常驻发送给 AI 的设定文字：《公共妓女》《灰色と青》的基础手稿、《伴星》《理》的人物散文、沙盒卡的世界基底。只放常驻散文，没有任何关键词触发开关（按需内容一律归入组件 3）。
- **第二层内页形态（左章节目录 + 右文稿纸 + 底部分页栏）**：
  - **左侧章节目录（`.toc`）**：按顺序列出各章节标题与字数，底部汇总全文字数与每轮常驻 Token 估算。
  - **右侧文稿纸（`.sheet`）**：无干扰的章节标题与大号散文编辑区（正文槽只装散文与 Markdown；YAML、JSON、键值缩进一律不进正文）。
  - **底部分页与「移入暗线与词条 ↗」动作（`.pager`）**：除上一章/下一章切换、复制、删除外，提供 **`移入暗线与词条 ↗`** 按钮——一键将当前章节从常驻文稿中剥离，自动截取首句作为 `hook` 转入 `[暗线与词条]` 组件（若未挂载则自动挂载），直接解决作者重构冗长常驻设定时的分拣诉求。
- **Runtime 映射**：
  - 映射为 `Card.fiction` 中的常驻 `Fragment`（无 `when` 条件，章节标题即 `Fragment.label`，位于 `Head` 缓存区内）。

#### 组件 2：`[开场与视角]`（`opening` — Openings & Frame Coordinates）
- **创作定位**：放置开场白（Node 0），以及整张卡最核心的交互通道与视角坐标。
- **第二层内页形态（左视角通道栏 + 右横向并排开场卡列）**：
  - **左侧：视角与交互通道（`.pov`）**：
    - 玩家输入通道切换：`剧内角色（input: "act"，玩家作为故事内角色说话行动）` vs `场外导演（input: "note"，玩家无实体角色，输入均为给叙述者的幕后指示）`。
    - 两个按需展开的折叠项（`<details class="fold">`，未填时标示「跟随全局偏好」）：`默认玩家身份描述（frame.persona）` 与 `卡片专属文风补充（frame.style / pov / voice）`。
  - **右侧：横向并排开场卡列（`.ocols`）**：
    - 每个开场是一张独立纵向卡片：顶部为开场短标题与「默认开场」单选钮；中部为**单一完整的开场正文框**（不再拆成时间/地点/旁白/台词碎格子）；底部为**「从这里开始时，覆写这些初始状态」chips**（如 IF 线开局将好感度设为 `15`、心情设为 `低落`，对应 `Greeting.do`）。
- **Runtime 映射**：
  - `Card.greetings: Greeting[]`（`Greeting = { text, do?: Effect_[] }`）
  - `Card.input: "act" | "note"`
  - `Card.frame`（按需写入非空槽位）

### B 组：动态上下文（Context & Lookup — `lore.ts` + `context.ts`）

在 [`packages/runtime/src/lore.ts`](../packages/runtime/src/lore.ts) 与 [`packages/runtime/src/context.ts`](../packages/runtime/src/context.ts) 中，Runtime 已经将所有上下文条目收敛为了统一的 `ContextItem` 与 `ContextPolicy`（`access: { model, player }`、`activation: "always" | "on_demand"`、`residency: "turn" | "window" | "permanent"`）。

「单层按需词条」与「多层推进暗线」是同一个 schema 类型（`LoreEntry`）：一条单层词条点击「+ 加深一层」就会长成多层阶梯暗线，而单层词条也可以合法地带 `offer` 窗口。因此合并为唯一的 `[暗线与词条]` 组件，差异在**条目内部按层数动态呈现**：

#### 组件 3：`[暗线与词条]`（`lore` — Context Entries & Progressive Layers）
- **创作定位**：卡片自带的一切受状态控制、可按需读取的知识：AI 自主检索的词条、卡片级写作手法条目、玩家可手动点亮的卡片级 Skill，以及随剧情分层剥开的隐藏秘密。无传统关键词匹配。
- **第二层内页形态（左分组列表 + 右动态详情）**：
  - **左侧列表（`.llist`）**：支持按名称/首句索引搜索及按调取权限（`全部 / AI 检索 / 玩家点亮 / 双方皆可`）筛选；列表自动分组展示 **`暗线（多层）`** 与 **`单层词条`**。
  - **右侧详情（`.lmain`）**：
    - **所有条目共有的轻量头**：
      1. **首句索引（Hook）**：常驻在索引目录里的一句话描述（`lore.ts` 的 `hook`），AI 与玩家靠这句话决定是否翻开。
      2. **谁能调取（Access）**：`AI 自动检索`（`{ model: true, player: false }`）/ `玩家手动点亮`（`{ model: false, player: true }`）/ `双方皆可`（`{ model: true, player: true }`）。
      3. **驻留周期（Residency）**：`仅本轮有效 (turn)` / `滑窗保留 (window)` / `永久常驻 (permanent)`。
      4. **主动提示窗口（Offer，可选）**：满足什么条件时，导演主动把暗示递给本轮叙事者。
    - **当条目只有 1 层时**：直接展示干净的词条正文框，底部提供醒目的虚线按钮 **`+ 加深一层（转为渐进秘密）`**。
    - **当条目有 2 层及以上时**：原地展开顶部的**「揭示预演拉杆（`.sim`）」**与下方的**「阶梯视图（`.ladder`）」**——拉动模拟数值滑块即可实时点亮已解锁层；每一层配置解锁门槛（`unlock[n]`，跨过即沿路径单调保持）与该层揭示的正文。
- **Runtime 映射**：
  - `Card.lore: LoreEntry[]`（`layers`、`unlock`、`offer`、`ContextPolicy`）与 `Card.director`。

### C 组：数值与机制（Rules & Settlement — `card.ts`）

定义一个变量（`rules.fields`）、写不同数值区间的表现描写（`fiction[].when`）、以及写回合后怎么加减分（`rules.readouts`）在同一个组件内闭环完成：

#### 组件 4：`[状态与阶段]`（`state` — State Axis, Stage Bands & Readouts）
- **创作定位**：面向好感度、理智值、嫌疑度、线索数或心情枚举等核心状态轴，将「变量定义 + 阶段表现散文 + 回合后升降判据」收拢在同一视图内。
- **第二层内页形态（左字段列表 + 右三段式主区）**：
  - **左侧字段列表（`.fside`）**：列出所有数值区间字段与枚举字段，显示范围、阶段数与判据档数。
  - **右侧顶部：字段定义与可拖拽阈值分段尺（`.trk.big`）**：
    - 配置字段名、数值范围（`min–max`）、初始值（`initial`）及「玩家可见 / 仅 AI 可见」（`hidden`）。
    - **可拖拽阈值分段尺**：灰阶色块直观展示各阶段在数轴上的跨度与初始值三角标；**直接左右拖动黑色分界竖线（`.th`）即可实时调整阶段阈值**，点击任意区段切换下方编辑的阶段。
  - **右侧中部：纯粹的阶段表现散文框（`.stage-prose`）**：
    - 选中某个阶段后，下方提供支持拆分/合并阶段的头部栏，以及**单一纯粹的自由散文框**（绝不拆成称呼/语气/会做/不会做等填表小格），直接对应带 `when` 条件的 `Card.fiction` 切片。
  - **右侧底部：回合后升降判据（`.reads` — Readouts）**：
    - 顶部为一句总提问（`Readout.text`，如「这一幕里，林栖对玩家的态度如何变化？」）；
    - 下方为有序分档列表（`Readout.options`）：每行包含档位描述、数值变化量（`d`）以及以 `0` 为中轴的**正负双向迷你条形图（`.dbar`，左空心负、右实心正）**；枚举字段则直接下拉选择切换到的目标枚举值。
  - **与后端 `compile` 的原生咬合**：`compile` 生成的空白阶段框或空白判据框（触发 `empty-text` 门禁）直接就地显示在当前组件的阶段或判据行中，引导作者当场手填补齐。
- **Runtime 映射**：
  - `Card.rules.fields` + 关联该字段的 `Card.fiction[].when` + 关联该字段的 `Card.rules.readouts`。

#### 组件 5：`[行动与检定]`（`check` — Actions, Chance & Ending）

  - **顶部：终局与回合上限（`.endband`）**：

  - **下方：行动检定表（`.actlist`）**：
    - 每条行动包含：行动名称与描述、**浮现条件**（`常驻可选` / `满足状态条件时出现`）、**成功率算法**（三种模式切换：① `固定概率 %` ② `随状态变化` ③ `AI 按判据评判`）、**实时成功率预览条与「试掷」按钮**（联动右上角切片预览中的当前状态值）、以及**成功时（`hit`）与失败时（`miss`）的状态变更 chips**。

## 5. 评审结论

### 5.1 已决：`[受控角色表单]` 裁掉（2026-11-09）

- **理由。** GLOSSARY §45 的立场是散文被原样读到就是表达力，schema 的责任是对散文透明。《伴星》《理》正文里的键值缩进是 ST 导入卡的原样，本项目对这种习惯的处理是改写成散文（《竹林》）与按 `label` 分段（《盐道》的「官府与盐帮」「眼下」）。做一个把键值序列化成文本的表单，是把这个习惯制度化。裁掉后，导入卡的键值块原样放进 `[设定文稿]`，作者下次修订时改成几章散文。
- **随之定下的立场**：正文槽只装散文与 Markdown，不再有 YAML、JSON 或键值缩进；GUI 永远不反解析文本。结构化的东西各有自己的家：字段与读数在 `rules`，表与记录在 `products`，条件是 Cond。
- **后续可选的代码锁**：一条 warn 级 lint，正文槽里连续多行 `key: value` 缩进即提示改写；《伴星》《理》会因此亮灯，这正是它们该被改写的记号。
- 原提案留档：

1. **`[受控角色表单]` 在 `Card` YAML 中的序列化与反解析约定**
   - 当作者在 GUI 中使用 `[受控角色表单]` 填写了结构化的角色属性（如「姓名」「性格」「外貌」「经历」），保存为 `Card` 时：
     - **方案 A（零 Schema 改动，约定 Markdown/YAML 块格式）**：将其序列化为 `Card.fiction` 中一段带固定标题约定（例如以 `## 角色：<名字>` 开头、内部为标准 `Key: Value` 列表）的 `Fragment`。前端打开卡片时，通过轻量 Parser 识别该格式并还原为 `[受控角色表单]` 组件；无法识别的普通段落则自动作为 `[设定文稿]` 呈现。
     - **方案 B（显式元数据或子类型）**：在 `Fragment` 上允许一个可选的描述性标记或结构化字段，省去文本反解析。
   - 倾向于讨论哪种方式更符合 Runtime 极简原则且最稳健。

2. **lore 的分流规则** —— **已解决**：不分流，一个组件（`[暗线与词条]`），条目内按声明露出（单层词条点「+ 加深一层」即展开阶梯与揭示预演，见组件 3）。`!offer` 作为判据本来就不成立。

3. **二维画布顺序、`Card.fiction` 装配顺序与布局持久化** —— **已解决（2026-11-09 原型对齐）**：
   - **唯一落点与内部顺序**：每类组件在二维画布上最多挂载 1 个实例。常驻无条件 `Fragment` 的先后顺序由组件 1 `[设定文稿]` 内部的章节顺序决定（全部位于 `Head` 缓存区内）；带 `when` 条件的阶段 `Fragment` 由组件 4 `[状态与阶段]` 内的字段与阶段顺序决定（按需进入 `Turn`）。跨组件需要引用画布顺序时，二维网格一律按**先行后列（row-major reading order）**读取。
   - **布局持久化归属**：二维画布的行列结构与宽高分数（`layout: { rows: { h, items: { id, w }[] }[] }`）属于工坊视图层（author chrome），按 `card id` 持久化在草稿存储（`drafts`）中，不进入运行时 `Card` Schema。
